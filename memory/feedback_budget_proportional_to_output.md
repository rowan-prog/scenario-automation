**사용자 (2026-08-27):** *"산출물량, 산출 퀄리티 대비 작업소요 시간과 토큰 소모량이 과다하다. 1/10로 줄여도 모자라다. 러프 기획안은 a4 1장짜리 산출물인데, 이렇게 많은 프로세스, 작업 시간, 토큰 소모를 하는 것은 설계 의도에서 많이 벗어났다."*

**실측 (29 v6 보험사 개정 · A4 1장):** subagent 12기 — 작성 5기(트리트먼트·셀링·로그라인 3프레이밍 × 각 80k) + haiku 되감기 3회 + sonnet 로그라인 판정 130k + sonnet 45항 체크리스트 2회 230k + 재생성 — 약 **110만 토큰 · 45분**. 산출물은 로그라인 한 줄 + 셀링 6 + 트리트먼트 8화.

**Why:** 같은 날 오전에 설계한 절차가 "단일 agent 금지·생성≠판정≠되감기"를 **산출물 크기와 무관하게** 풀 벨트로 돌게 만들었다. 유닛을 나누면 유닛마다 표준·코퍼스를 재정독하고(5 × 30k), 후보를 36개 만들면 판정에 130k가 들고, 45항 체크리스트는 A4 한 장에도 45행을 쓴다. 분리·검증 원칙은 맞지만 **예산 상한이 없으면 절차가 스스로 커진다.**

**How to apply:**
- **상한표 = `config/WORKFLOW_MAP.md` §0-1** (하드 · 초과 = 중단·보고): 로그라인 ≤2기·40k·2분 / **러프 기획안 ≤2기·80k·3분** / 플랫폼 기획안 ≤6기·300k·15분 / 집필·각색 배치 ≤5기·300k·15분. **시간의 기준 = opus가 A4 한 장 쓰는 데 1분, haiku가 읽는 데 30초 — 그 이상은 절차가 만든 시간.** 사용자 2차: *"러프 기획안은... 5분도 긴데?"* → 10분을 3분으로.
- **agent에 표준 파일을 정독시키지 않는다.** 유닛마다 표준 5개를 열면 2~3분이 거기서 나간다. 규칙은 지시서에 인라인(골격표·금지 7종·문장 규격 20줄), agent가 여는 파일 = p0·원안·원작 해당 EP뿐.
- **A4 한 장은 메인이 직접 본다.** 체크리스트 유닛(proposal-spec-auditor)·sonnet 판정 유닛(logline-auditor)은 플랫폼 기획안·작가 발송본 전용. 러프 = lint·grep + haiku 되감기 1회 + 메인 10항.
- **작성 유닛은 산출물당 1기** — opus 1기가 로그라인 후보 3 + 셀링 + 트리트먼트를 통째로 쓰고 파일에 직접 저장. 메인이 p0 전문을 다시 타이핑하지 않는다.
- **후보 ≤10 · 프레이밍 1개에 필수 요소 3개 명시** · 재라운드 자동 트리거 금지(문장 단위 수정) · 라운드 파일·판정표 생성 금지.
- agent 정독 지시 = 표준 골격표·등재 예시만. 코퍼스 전량 정독은 표준 제정 때 한 번.
- 새 절차를 설계할 때 먼저 물을 것: **산출물이 몇 장인가 → agent 몇 기가 정상인가.** 품질은 게이트가 만들지 호출 수가 만들지 않는다.
